# BUG.md

Tracking of reproducible bugs. Compliant with Vidocq conventions (AGENTS.md § "Reproducible bugs tracked in BUG.md").

| id | date | symptom | repro | hypothesis | status |
|---|---|---|---|---|---|
| BUG-001 | 2026-05-15 | **Potential virtual thread leak** under `@Asynchronous + @Timeout` with a long-running `CompletionStage` | Method `@Asynchronous @Timeout(100ms)` returning `CompletableFuture.supplyAsync(() -> Thread.sleep(5000))`: `TimeoutEngine` stops after 100ms and throws `TimeoutException`, but the unwrap thread (`stage.toCompletableFuture().get()`) keeps blocking for up to 5s before being collected | The `get()` call is not interruptible via `Thread.interrupt()` on all `CompletableFuture` implementations (depends on the underlying chain). With virtual threads, the leak is minor (a few KB of memory) and resolves on its own when the task expires. Acceptable until a future optimization with `StructuredTaskScope` (finalized in Java 25) if benchmarks justify it. | ⚠️ accepted — optional M10+ optimization |
| BUG-002 | 2026-05-25 | **Java Modules bypassed**: `maven-dependency-plugin` copies compile-scope JARs into `target/javamodules/` and the compiler receives a manual `--module-path` instead of relying on Maven native Java Modules resolution | `grep "javamodules" pom.xml` reveals the config ; remove the `maven-dependency-plugin` section and rebuild to observe the `module not found` errors | `microprofile-fault-tolerance-api`, `vauban-core`/`vauban-classloader-spi`, and `jmh-core` do not have a `module-info.class` recognized by `maven-compiler-plugin` 4.x for automatic placement on the module path | ⚠️ OPEN — workaround active ; to be removed module by module as upstream dependencies become modularized or wrapped (see the `heisenberg-mp-ft-api` pattern) |
| BUG-003 | 2026-10-08 | **`@Fallback(fallbackMethod = ...)` fails on the strict module path**: an application in a named module that opens nothing cannot deploy a bean with a fallback method — `HeisenbergExtension` validation throws `FaultToleranceDefinitionException: Invalid fallbackMethod` caused by `IllegalAccessException: module io.vidocq.heisenberg.core does not read module <app>`. Any access modifier fails, not only `private` | `heisenberg-cdi-vauban-module-it`: `FallbackService` (private and package-private fallback methods) + `FallbackMethodModulePathTest` | `FallbackResolver` takes `MethodHandles.privateLookupIn(owner, lookup())` from `io.vidocq.heisenberg.core`, which needs a read edge to the application module AND the package opened to the core. The official TCK runs on the class path (unnamed module), where both hold, so 463/463 never saw it; the heisenberg-core / heisenberg-cdi-vauban unit tests ran on the class path too until the late module-info workaround was removed | ✅ FIXED (branch `pr/ybl/module-info-in-place`, needs vauban `pr/ybl/module-lookup-for-extensions`) — `FallbackResolver` asks a container hook (`FallbackResolver.LookupSource`) for a lookup on the bean class; heisenberg-cdi-vauban implements it with Vauban's `ModuleLookups`, whose lookup comes from the generated `_VaubanComponents` of the bean's package, processor- or plugin-written (same module: no read, no opens). Without a lookup, the core adds the read edge itself, so `opens <pkg> to io.vidocq.heisenberg.core` alone is enough (covered by the heisenberg-cdi-vauban tests, which call the interceptor without a container) |
| BUG-004 | 2026-10-09 | **Fault Tolerance does nothing under Weld SE** (heisenberg#25): `heisenberg-cdi-vauban` ships no `META-INF/beans.xml`, so it is an implicit bean archive, which Weld SE does not scan by default. `FaultToleranceInterceptor`, `FaultTolerancePriority3850Interceptor`, the state registries and the metrics recorders are not discovered, and `@Retry`, `@Timeout` and the others are silently ignored | `jar tf heisenberg-cdi-vauban-*.jar \| grep beans.xml` finds nothing; `BeanArchiveTest.isAnAnnotatedBeanArchive` fails on `main` with `missing target/classes/META-INF/beans.xml` | Every test and the TCK run on Vauban, which is told about these beans; no test ran on another container | ✅ FIXED (branch `fix/25-bean-archives`) — `META-INF/beans.xml` with `bean-discovery-mode="annotated"`; every bean class already carries a bean-defining annotation (`@Interceptor` or `@ApplicationScoped`). `BeanArchiveTest` also checks that every non-Vauban `provides` is listed in `META-INF/services`. A Weld SE and an OpenLiberty integration test follow in heisenberg#25 |
| BUG-005 | 2026-10-10 | **An application with Fault Tolerance but without Metrics or Telemetry does not start**: `vidocq create -x heisenberg-fault-tolerance` alone fails at container build with `NoClassDefFoundError: org/eclipse/microprofile/metrics/MetricRegistry` (Vauban `BeanDiscovery.resolveGenericTypeForField` on `DiracFtMetricsRecorder.registry`); with Metrics present it fails next on `NoClassDefFoundError: io/opentelemetry/api/common/AttributeKey` (`OtelFtMetricsRecorder.<clinit>`). Not a regression: the published 0.3.0 fails the same way | `vidocq create --name ftonly -g io.example -x heisenberg-fault-tolerance`, then `mvn package vidocq:run` (0.4.0-SNAPSHOT, vauban 74449e5c + heisenberg 51e3dc7) or `mvn package vidocq:package` + `bin/ftonly.sh` with `--parent-version 0.3.0` | `DiracFtMetricsRecorder` and `OtelFtMetricsRecorder` are always-discovered `@ApplicationScoped` beans whose signatures reference the optional `microprofile.metrics.api` / `io.opentelemetry.api` modules (`requires static`). The `OtelFtMetricsRecorder` Javadoc assumes the container "silently ignores" a class it cannot load (Weld does, with `WELD-000119`); Vauban propagates the `NoClassDefFoundError` and aborts. Every test and the TCK run with Metrics and Telemetry on the path, so nothing caught it. Fix candidates: register each recorder only when its API module is present (build-compatible extension or a `provides` per recorder), and/or make Vauban skip, with a warning, a discovered class that fails to link | ✅ FIXED (branch `fix/ft-without-observability`) — the two recorder beans now extend `DelegatingFtMetricsRecorder` and refer to no Metrics / OpenTelemetry type; the API code moved to `DiracFtMetrics` and `OtelFtMetrics` (not beans), created in `@PostConstruct` only when the API can be loaded and read. `DiracFtMetrics` looks the base-scope registry up through `@Any Instance<Object>` and falls back to NOOP when no registry bean exists. `MetricsRecorderResolver` leaves inactive recorders out, so no observability still resolves to NOOP. Covered by `MetricsRecordersWithoutObservabilityTest` (module path, neither API). The Vauban side (skip a discovered class that fails to link, as Weld does) is left open |
